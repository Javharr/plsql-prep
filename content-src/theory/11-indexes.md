## Зачем нужен индекс

Без индекса, чтобы найти строку с `employee_id = 150`, Oracle читает таблицу целиком — **полное сканирование** (TABLE ACCESS FULL). Индекс — отдельная структура, где значения столбца хранятся **упорядоченно** вместе с **ROWID** — физическим адресом строки. Найти значение в упорядоченной структуре можно за несколько шагов, а по ROWID — сразу прочитать нужный блок таблицы.

Аналогия — предметный указатель в конце книги: термин → номер страницы.

## B-tree — индекс по умолчанию

`CREATE INDEX emp_dept_ix ON employees (department_id);` создаёт **B-дерево** (сбалансированное дерево):

- **корневой** и **ветвящиеся** блоки хранят диапазоны ключей и ссылки вниз;
- **листовые** блоки хранят пары «значение — ROWID», отсортированные и связанные между собой в двусвязный список (поэтому удобно читать диапазоны).

Высота дерева обычно 2–4 уровня даже для миллионов строк — поиск значения стоит несколько чтений блоков.

Способы доступа, которые видны в плане:

| Операция | Когда |
|---|---|
| `INDEX UNIQUE SCAN` | равенство по уникальному индексу — максимум одна строка |
| `INDEX RANGE SCAN` | диапазон, неуникальное равенство, `LIKE 'abc%'` |
| `INDEX FULL SCAN` | весь индекс по порядку (например, чтобы избежать сортировки) |
| `INDEX FAST FULL SCAN` | весь индекс без порядка, как маленькая таблица — если все нужные столбцы есть в индексе |
| `INDEX SKIP SCAN` | по составному индексу без первого столбца (если у первого мало разных значений) |

> **NULL в B-tree:** если **все** столбцы ключа NULL, строка в B-tree индекс не попадает. Поэтому `WHERE col IS NULL` по обычному однострочному индексу не ищется. Обход — составной индекс с константой: `(col, 0)`.

## Bitmap-индексы

Для каждого значения хранится битовая карта: бит на каждую строку. Хороши для столбцов с **малым числом разных значений** (пол, статус, регион) в **хранилищах данных**: битовые карты быстро комбинируются через AND/OR для сложных фильтров.

Плохи для OLTP: один бит-карта покрывает много строк, и изменение одной строки блокирует целый кусок карты — параллельные вставки и обновления начинают ждать друг друга и ловить deadlock.

## Составные и функциональные индексы

**Составной индекс** — по нескольким столбцам: `(last_name, first_name)`. Порядок столбцов важен:

- он отлично работает для `WHERE last_name = … AND first_name = …` и для `WHERE last_name = …`;
- для `WHERE first_name = …` — только через skip scan или вообще не используется.

Правило: первым ставят столбец, который чаще всего есть в условиях на равенство; диапазонные условия — правее.

**Функциональный индекс** — по выражению. Обычный индекс по `last_name` не поможет условию `UPPER(last_name) = 'KING'`, а такой поможет:

```sql
CREATE INDEX emp_upper_name_ix ON employees (UPPER(last_name));
```

Выражение в запросе должно совпадать с выражением индекса. Пользовательские функции в индексе должны быть `DETERMINISTIC`.

**Покрывающий индекс** — если в индексе есть все столбцы, которые нужны запросу, Oracle вообще не ходит в таблицу (нет шага `TABLE ACCESS BY INDEX ROWID`).

## Когда индекс НЕ используется

Частые причины:

1. **Функция или выражение над индексированным столбцом:** `WHERE TRUNC(hire_date) = DATE '2024-01-01'`, `WHERE salary * 12 > 100000`. Перепиши в диапазон: `hire_date >= DATE '2024-01-01' AND hire_date < DATE '2024-01-02'`.
2. **Неявное преобразование типа:** столбец `VARCHAR2`, а сравнивают с числом `WHERE phone = 12345` — Oracle применит `TO_NUMBER(phone)`, и индекс выключится.
3. `LIKE '%abc'` — поиск с начальным `%`: дерево упорядочено по началу строки.
4. `IS NULL` по однострочному индексу (NULL не хранится).
5. `<>`, `NOT IN` — обычно выгоднее полное сканирование.
6. **Низкая селективность:** запрос возвращает заметную долю таблицы — полное сканирование читает блоки большими порциями и выходит дешевле, чем тысячи переходов по ROWID. Оптимизатор считает это по статистике.
7. Устаревшая или отсутствующая статистика.
8. Первый столбец составного индекса не участвует в условии.

## Цена индексов

Индекс ускоряет чтение, но:

- **замедляет INSERT, UPDATE индексированных столбцов и DELETE** — каждое изменение правит и таблицу, и все её индексы;
- занимает место;
- лишние и дублирующие индексы мешают оптимизатору.

Поэтому индекс ставят под конкретные запросы: PK и UNIQUE (автоматически), внешние ключи, частые условия поиска и соединения. Неиспользуемые индексы находят мониторингом (`ALTER INDEX … MONITORING USAGE`, в новых версиях — `DBA_INDEX_USAGE`).

Ещё варианты: **невидимый индекс** (`INVISIBLE`) — существует и поддерживается, но оптимизатор его не видит; удобно проверить, что будет без индекса. **Reverse key** — против конкуренции за последний листовой блок при вставке растущих ключей.

## ? Что такое индекс и как устроен B-tree?

Отдельная структура, которая хранит значения столбца в отсортированном виде с ROWID — адресом строки. B-tree — сбалансированное дерево: корень и ветви указывают диапазоны, листья хранят пары «значение — ROWID» и связаны между собой, поэтому удобно и искать значение, и читать диапазон. Высота обычно 2–4 уровня.

## ? Когда индекс не используется, хотя он есть?

Функция или выражение над столбцом (`TRUNC(date)`, `UPPER(name)`) без соответствующего функционального индекса; неявное преобразование типа (строку сравнивают с числом); `LIKE '%…'`; `IS NULL` по однострочному индексу; условие не по первому столбцу составного индекса; запрос выбирает большую долю строк и полное сканирование дешевле; плохая статистика.

## ? Чем B-tree отличается от bitmap-индекса?

B-tree хранит значение и ROWID для каждой строки, подходит для столбцов с большим числом разных значений и для OLTP. Bitmap хранит битовую карту на каждое значение, компактен для столбцов с малым числом значений и хорош для DWH, где комбинируют много фильтров. В OLTP bitmap опасен: изменение одной строки блокирует часть карты, параллельные DML начинают ждать.

## ? Что такое функциональный индекс?

Индекс по выражению, например `UPPER(last_name)` или `TRUNC(hire_date)`. Используется, когда в условии стоит ровно такое же выражение. Функции пользователя в нём должны быть DETERMINISTIC.

## ? Важен ли порядок столбцов в составном индексе?

Да. Индекс `(a, b)` отсортирован сначала по a, потом по b. Он хорошо работает для условий по a и по a + b, а для условия только по b — максимум skip scan. Первым ставят столбец, который чаще участвует в условиях-равенствах; столбцы с диапазонными условиями — дальше.

## ? Почему не стоит создавать индексы на всё подряд?

Каждый индекс замедляет INSERT, DELETE и UPDATE индексированных столбцов: Oracle правит и таблицу, и все индексы. Индексы занимают место, а лишние ещё и сбивают оптимизатор. Индексируют PK, UNIQUE, внешние ключи и столбцы реальных частых условий поиска и соединения.

## ? Что такое ROWID?

Физический адрес строки: объект, файл, блок и номер строки в блоке. Доступ по ROWID — самый быстрый способ достать строку, на нём и держатся индексы (листья хранят ROWID). ROWID может измениться при перемещении строки (MOVE таблицы, секционирование), поэтому хранить его как постоянный ключ нельзя.

## Тест: Есть индекс на hire_date. Какое условие сможет его использовать?
- WHERE TRUNC(hire_date) = DATE '2020-01-15'
- WHERE TO_CHAR(hire_date, 'YYYY') = '2020'
- [x] WHERE hire_date >= DATE '2020-01-01' AND hire_date < DATE '2021-01-01'
- WHERE hire_date + 30 > SYSDATE
> Функция или выражение над столбцом выключает обычный индекс. Диапазон по «голому» столбцу — индекс работает.

## Тест: Столбец phone VARCHAR2 с индексом. Почему WHERE phone = 5551234 не использует индекс?
- Числа нельзя сравнивать со строками
- [x] Oracle неявно применяет TO_NUMBER к столбцу, и индекс по phone не подходит
- Индекс не работает с равенством
- Нужен bitmap-индекс
> При сравнении строки с числом Oracle конвертирует строку в число — то есть оборачивает столбец функцией. Пиши `phone = '5551234'`.

## Тест: Индекс по (last_name, first_name). Для какого условия он наименее полезен?
- WHERE last_name = 'King'
- WHERE last_name = 'King' AND first_name = 'Steven'
- [x] WHERE first_name = 'Steven'
- WHERE last_name LIKE 'Ki%'
> Индекс упорядочен сначала по last_name. Без условия на первый столбец — в лучшем случае skip scan, чаще полное сканирование.

## Тест: Для какого случая лучше подходит bitmap-индекс?
- Столбец email в таблице пользователей интернет-магазина
- [x] Столбец region (10 значений) в большой таблице фактов хранилища данных
- Первичный ключ таблицы заказов
- Столбец статуса заказа, который постоянно обновляют сотни сессий
> Bitmap хорош для малого числа значений и редких изменений (DWH). При активных параллельных DML он вызывает блокировки.

## Тест: Найдёт ли обычный B-tree индекс по commission_pct строки для WHERE commission_pct IS NULL?
- Да, всегда
- [x] Нет: строки, где весь ключ NULL, в B-tree индекс не попадают
- Да, если индекс уникальный
- Только для числовых столбцов
> Однострочный B-tree не хранит NULL-ключи. Обход — составной индекс `(commission_pct, 0)` или функциональный.

## Тест: Какая операция чтения не обращается к таблице вообще?
- TABLE ACCESS BY INDEX ROWID
- [x] INDEX FAST FULL SCAN, если все нужные столбцы есть в индексе
- TABLE ACCESS FULL
- INDEX RANGE SCAN с последующим чтением строк
> Если индекс покрывает запрос, Oracle читает только его — таблица не нужна.

## Тест: Как индексы влияют на INSERT?
- Ускоряют
- Никак
- [x] Замедляют: при вставке нужно обновить каждый индекс таблицы
- Замедляют только уникальные
> Каждая вставка — запись в таблицу плюс запись в каждый индекс. Чем больше индексов, тем дороже DML.
