## Аномалии параллельной работы

Когда транзакции работают одновременно, возможны «аномалии»:

| Аномалия | Что происходит |
|---|---|
| **Грязное чтение** (dirty read) | читаешь данные, которые другая транзакция изменила, но ещё **не закоммитила** (и может откатить) |
| **Неповторяющееся чтение** (non-repeatable read) | читаешь строку дважды в одной транзакции — между чтениями её изменили и закоммитили, значения разные |
| **Фантомное чтение** (phantom read) | повторяешь запрос с условием — появились **новые строки**, которые другая транзакция вставила и закоммитила |
| **Потерянное обновление** (lost update) | две транзакции читают значение, каждая считает новое и записывает; второе обновление затирает первое |

## Четыре уровня изоляции (стандарт SQL)

| Уровень | Грязное | Неповторяющееся | Фантомы |
|---|---|---|---|
| READ UNCOMMITTED | возможно | возможно | возможно |
| READ COMMITTED | — | возможно | возможно |
| REPEATABLE READ | — | — | возможно |
| SERIALIZABLE | — | — | — |

Чем выше уровень, тем меньше аномалий и тем больше ожиданий или ошибок сериализации.

## Что из этого есть в Oracle

- **READ COMMITTED** — уровень **по умолчанию**. Каждый *запрос* видит данные, закоммиченные на момент **начала этого запроса**.
- **SERIALIZABLE** — вся *транзакция* видит данные на момент её начала (плюс свои изменения). Если пытаешься изменить строку, которую после начала твоей транзакции изменил и закоммитил другой — ошибка `ORA-08177: can't serialize access for this transaction`.
- **READ ONLY** — как SERIALIZABLE, но только чтение. Удобно для отчёта, где все запросы должны видеть один снимок.
- **READ UNCOMMITTED нет**: грязного чтения в Oracle не бывает никогда. **REPEATABLE READ** как отдельного уровня тоже нет — его поведение покрывает SERIALIZABLE.

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;   -- первой командой транзакции
SET TRANSACTION READ ONLY;
ALTER SESSION SET ISOLATION_LEVEL = SERIALIZABLE;
```

## Согласованное чтение (MVCC)

Oracle — СУБД с **многоверсионностью** (MVCC). Изменяя блок, транзакция сохраняет старую версию в undo. Запрос, начавшийся раньше, получает согласованный снимок: если блок изменён позже начала запроса, Oracle восстанавливает его прошлую версию из undo.

Отсюда главный принцип Oracle: **читатели не блокируют писателей, писатели не блокируют читателей**. `SELECT` никогда не ждёт `UPDATE` и не ставит блокировок (кроме `SELECT … FOR UPDATE`). Ждать друг друга могут только два **писателя** одной и той же строки.

## Блокировки

- DML ставит **блокировку строки** (TX) — только на изменяемые строки, а не на страницу или таблицу. Эскалации блокировок в Oracle нет: хоть миллион строк — это миллион блокировок строк, без перехода на таблицу.
- Плюс **блокировку таблицы** (TM) в разделяемом режиме — чтобы во время твоей транзакции никто не сделал `DROP` или `ALTER` таблицы.
- Блокировки держатся **до конца транзакции** (COMMIT/ROLLBACK).
- Вторая сессия, которая хочет изменить ту же строку, **ждёт**. С `SELECT … FOR UPDATE NOWAIT` — сразу ошибка ORA-00054, с `WAIT n` — ждёт n секунд.

## Потерянное обновление и SELECT FOR UPDATE

```sql
-- сессии A и B одновременно:
SELECT balance INTO v_bal FROM accounts WHERE id = 1;   -- обе прочитали 100
UPDATE accounts SET balance = v_bal - 30 WHERE id = 1;  -- A записала 70, B записала 70
```

Списали 30 дважды, а баланс уменьшился один раз. Решения:

1. **Пессимистичная блокировка** — `SELECT … FOR UPDATE`: строка блокируется при чтении, вторая сессия ждёт, пока первая закончит.
2. **Обновление одной командой** — `UPDATE accounts SET balance = balance - 30` без предварительного чтения в переменную.
3. **Оптимистичная** — столбец версии: `UPDATE … SET balance = :new, ver = ver + 1 WHERE id = 1 AND ver = :old_ver`; если обновилось 0 строк — кто-то успел раньше, перечитать и повторить.

`FOR UPDATE OF col SKIP LOCKED` — пропускать уже заблокированные строки; так разбирают очередь задач несколькими обработчиками.

## Deadlock

Взаимная блокировка: A держит строку 1 и ждёт строку 2, B держит строку 2 и ждёт строку 1. Oracle сам находит deadlock за несколько секунд и **откатывает одну команду** (не всю транзакцию) в одной из сессий с ошибкой `ORA-00060: deadlock detected`. Транзакция этой сессии продолжает держать свои блокировки — ей нужно сделать ROLLBACK или повторить.

Как избежать: блокировать ресурсы **в одном и том же порядке** во всём коде (например, всегда по возрастанию id), держать транзакции короткими, индексировать внешние ключи (иначе блокируется вся дочерняя таблица).

## ? Какие уровни изоляции есть и какие поддерживает Oracle?

По стандарту: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE — от меньшей защиты к большей. Oracle поддерживает READ COMMITTED (по умолчанию), SERIALIZABLE и режим READ ONLY. Грязного чтения в Oracle не бывает вообще, а REPEATABLE READ отдельно не реализован.

## ? Объясни грязное, неповторяющееся и фантомное чтение.

Грязное — видишь чужие незакоммиченные изменения. Неповторяющееся — одна и та же строка при повторном чтении в транзакции изменилась, потому что другую транзакцию закоммитили. Фантомное — повторный запрос с тем же условием вернул новые строки, которые кто-то вставил и закоммитил. READ COMMITTED в Oracle защищает от первого; от всех трёх — SERIALIZABLE.

## ? Блокирует ли SELECT в Oracle строки? Ждёт ли SELECT, если строку изменяют?

Нет и нет. Обычный SELECT не ставит блокировок и не ждёт писателей: благодаря многоверсионности он читает последнюю закоммиченную версию на момент начала запроса, восстанавливая её из undo. Блокирует только SELECT … FOR UPDATE.

## ? Что такое deadlock и как Oracle с ним поступает?

Две (или больше) транзакции ждут друг друга по кругу. Oracle сам обнаруживает deadlock и откатывает текущую команду одной из сессий с ORA-00060; её транзакция не откатывается целиком и блокировки остаются — сессия должна сделать ROLLBACK или повторить. Профилактика — единый порядок блокировок, короткие транзакции, индексы на FK.

## ? Что такое потерянное обновление и как от него защититься?

Две сессии прочитали одно значение, каждая записала своё, вычисленное от прочитанного, — одно изменение потерялось. Защита: SELECT … FOR UPDATE (пессимистичная блокировка), изменение одной командой `SET x = x - 30`, или оптимистичная блокировка по столбцу версии с проверкой количества обновлённых строк.

## ? Чем READ COMMITTED отличается от SERIALIZABLE в Oracle?

В READ COMMITTED согласованный снимок берётся на начало каждого запроса: два запроса в одной транзакции могут видеть разные данные. В SERIALIZABLE снимок на начало транзакции: все её запросы видят одно и то же состояние, а попытка изменить строку, изменённую другими после начала, даёт ORA-08177 — приложение должно повторить транзакцию.

## Тест: Как правильнее списать 30 с баланса, чтобы не потерять параллельное списание?
- SELECT balance INTO v, затем UPDATE SET balance = v - 30
- [x] UPDATE accounts SET balance = balance - 30 WHERE id = 1
- SET TRANSACTION READ ONLY перед UPDATE
- COMMIT перед каждым UPDATE
> Одна команда читает и пишет под блокировкой строки: вторая сессия подождёт и вычтет из уже обновлённого значения. Чтение в переменную без FOR UPDATE ведёт к потерянному обновлению.
