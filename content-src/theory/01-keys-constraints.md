## Реляционная модель в двух словах

Данные хранятся в **таблицах** (отношениях). Строка — один объект или факт, столбец — его свойство. Порядок строк в таблице не определён: если нужен порядок — только `ORDER BY`.

Связи между таблицами — не указатели, а **совпадающие значения**: в `employees.department_id` лежит то же число, что в `departments.department_id`. Чтобы база сама следила за корректностью таких данных, на таблицы вешают **ограничения целостности** (constraints).

В Oracle пять видов ограничений:

| Ограничение | Что гарантирует |
|---|---|
| `NOT NULL` | в столбце всегда есть значение |
| `UNIQUE` | значения не повторяются (NULL можно, и несколько) |
| `PRIMARY KEY` | уникально и не NULL, у таблицы максимум один |
| `FOREIGN KEY` | значение есть в родительской таблице (или NULL) |
| `CHECK` | строка удовлетворяет условию, например `salary > 0` |

## Первичный ключ (PRIMARY KEY)

Первичный ключ однозначно идентифицирует строку. Это `UNIQUE + NOT NULL`, и у таблицы он **один** (но может состоять из нескольких столбцов — составной ключ).

```sql
CREATE TABLE departments (
  department_id   NUMBER(4)    CONSTRAINT dept_pk PRIMARY KEY,
  department_name VARCHAR2(30) NOT NULL
);
```

При создании PK Oracle автоматически создаёт **уникальный индекс** на этих столбцах (если подходящего индекса ещё нет). Поэтому поиск по PK всегда быстрый.

**Потенциальный ключ** (candidate key) — любой минимальный набор столбцов, однозначно определяющий строку. Один из них назначают первичным, остальные обычно закрывают `UNIQUE`.

## Естественный и суррогатный ключ

- **Естественный** ключ — значение из предметной области: ИНН, номер паспорта, email, код страны `UZ`.
- **Суррогатный** — искусственный номер без смысла: `id`, который выдаёт последовательность или `GENERATED AS IDENTITY`.

```sql
CREATE TABLE customers (
  cust_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email   VARCHAR2(100) NOT NULL CONSTRAINT cust_email_uk UNIQUE
);
```

Почему чаще берут суррогатный: естественные значения **меняются** (человек сменил паспорт или почту), бывают длинными и составными, а на PK ссылаются внешние ключи из других таблиц — менять его каскадом больно. При этом естественный ключ всё равно закрывают `UNIQUE`, иначе появятся дубли клиентов с разными id.

## Внешний ключ (FOREIGN KEY)

Внешний ключ говорит: значение этого столбца должно существовать в родительской таблице (в её PK или UNIQUE), либо быть NULL.

```sql
ALTER TABLE employees ADD CONSTRAINT emp_dept_fk
  FOREIGN KEY (department_id) REFERENCES departments (department_id);
```

Что будет при удалении родителя, на которого ссылаются:

| Вариант | Поведение |
|---|---|
| по умолчанию (NO ACTION) | ошибка `ORA-02292: integrity constraint violated - child record found` |
| `ON DELETE CASCADE` | вместе с родителем удаляются все дочерние строки |
| `ON DELETE SET NULL` | у дочерних строк FK становится NULL |

`ON UPDATE CASCADE` в Oracle **нет** — ещё одна причина не менять первичные ключи.

> **Ловушка про индексы:** Oracle **не** создаёт индекс на столбцах внешнего ключа автоматически. Без индекса удаление или изменение ключа родителя заставляет сканировать всю дочернюю таблицу и может блокировать её целиком. Индексы на FK ставят почти всегда.

## UNIQUE, CHECK, NOT NULL

**UNIQUE** запрещает повторы, но **NULL допускает**, причём несколько: NULL не равен NULL, поэтому две строки с NULL не считаются дублями. (Для составного UNIQUE строки, где *все* столбцы NULL, тоже не конфликтуют.)

**CHECK** — произвольное условие над значениями **одной строки**:

```sql
ALTER TABLE employees ADD CONSTRAINT emp_salary_ck CHECK (salary > 0);
ALTER TABLE employees ADD CONSTRAINT emp_dates_ck CHECK (end_date IS NULL OR end_date >= hire_date);
```

Ограничение CHECK не может ссылаться на другие строки или таблицы, на `SYSDATE`, последовательности и пользовательские функции. Если условие даёт UNKNOWN (из-за NULL) — строка **проходит**: CHECK отвергает только FALSE.

**NOT NULL** — на самом деле тоже CHECK (`столбец IS NOT NULL`), просто с отдельным синтаксисом.

## Управление ограничениями

Ограничения можно выключать и включать — например, для массовой загрузки:

```sql
ALTER TABLE employees DISABLE CONSTRAINT emp_dept_fk;
-- загрузка
ALTER TABLE employees ENABLE CONSTRAINT emp_dept_fk;           -- проверит все строки
ALTER TABLE employees ENABLE NOVALIDATE CONSTRAINT emp_dept_fk; -- только новые
```

**Отложенные** ограничения (`DEFERRABLE INITIALLY DEFERRED`) проверяются не при каждой команде, а при `COMMIT` — удобно, когда нужно временно нарушить связь внутри транзакции (например, поменять местами два значения).

Посмотреть ограничения таблицы — словарь `user_constraints` (тип: `P`, `R` — внешний, `U`, `C`) и `user_cons_columns`.

## ? Чем PRIMARY KEY отличается от UNIQUE?

- PK не допускает NULL, UNIQUE допускает (и несколько NULL одновременно).
- PK у таблицы один, UNIQUE-ограничений — сколько угодно.
- На PK по смыслу ссылаются внешние ключи (хотя FK может ссылаться и на UNIQUE).
- Оба создают уникальный индекс, если подходящего нет.

## ? Что такое внешний ключ и что будет при удалении родительской строки?

Ограничение, которое требует, чтобы значение было в родительской таблице (или NULL). При удалении родителя, у которого есть дети: по умолчанию — ошибка ORA-02292; с `ON DELETE CASCADE` — дети удалятся вместе с ним; с `ON DELETE SET NULL` — у детей FK обнулится. `ON UPDATE CASCADE` в Oracle нет.

## ? Нужно ли индексировать внешние ключи?

Почти всегда да. Oracle сам индекс на FK не создаёт. Без него: соединение родителя с детьми идёт полным сканированием, а удаление или изменение ключа в родителе заставляет проверить всю дочернюю таблицу и ставит на неё блокировку уровня таблицы — в нагруженной системе это вызывает ожидания и даже deadlock.

## ? Суррогатный или естественный ключ — что выбрать?

Обычно суррогатный (`IDENTITY` или последовательность) как PK: он короткий, неизменный и ничего не значит, поэтому его не придётся обновлять каскадом. Естественный ключ (email, ИНН) при этом закрывают `UNIQUE`, чтобы не было дублей. Естественный PK уместен для стабильных справочников: коды стран, валют.

## ? Можно ли вставить NULL в столбец с UNIQUE?

Да, и даже несколько строк с NULL: NULL не равен NULL, поэтому дублями они не считаются. Если NULL недопустим — добавляют `NOT NULL`. Для PK это уже встроено.

## ? Что пропускает ограничение CHECK, если в условии NULL?

Пропускает. CHECK отвергает строку только когда условие FALSE, а `NULL > 0` — это UNKNOWN. Поэтому `CHECK (salary > 0)` не мешает вставить `salary = NULL`; если NULL нельзя — нужен ещё `NOT NULL`.

## Тест: Сколько строк с NULL можно вставить в столбец с ограничением UNIQUE (без NOT NULL)?
- Ни одной
- Только одну
- [x] Сколько угодно
- Зависит от типа столбца
> NULL не равен никакому значению, в том числе другому NULL, поэтому UNIQUE не считает их повтором. Запретить NULL может только `NOT NULL`.

## Тест: Какой индекс Oracle создаёт автоматически?
- На столбцах внешнего ключа
- [x] На столбцах первичного ключа
- На всех столбцах с NOT NULL
- Никакой, индексы всегда создаются вручную
> PK и UNIQUE автоматически получают уникальный индекс. На внешний ключ индекс **не** создаётся — его ставят руками.

## Тест: Удаляем отдел, в котором есть сотрудники. FK объявлен без опций. Что произойдёт?
- Сотрудники удалятся вместе с отделом
- У сотрудников department_id станет NULL
- [x] Ошибка ORA-02292, отдел не удалится
- Отдел удалится, сотрудники останутся со старым номером
> Поведение по умолчанию — запрет: «child record found». Каскад и обнуление включаются только явно: `ON DELETE CASCADE` / `ON DELETE SET NULL`.

## Тест: Есть CHECK (salary > 0). Можно ли вставить строку с salary = NULL?
- [x] Да, CHECK пропускает UNKNOWN
- Нет, NULL нарушает условие
- Только если столбец объявлен с DEFAULT
- Нет, будет ORA-01400
> `NULL > 0` даёт UNKNOWN, а CHECK отвергает только FALSE. Чтобы запретить NULL, нужно `NOT NULL` (ORA-01400 — это как раз его ошибка).

## Тест: Чего нет в Oracle?
- ON DELETE CASCADE
- ON DELETE SET NULL
- [x] ON UPDATE CASCADE
- Отложенных (DEFERRABLE) ограничений
> Каскадного обновления ключа в Oracle нет — первичные ключи не принято менять, для этого и берут суррогатные.

## Тест: Может ли ограничение CHECK сравнить значение с SYSDATE или с данными другой таблицы?
- Да, с обоими
- С SYSDATE да, с другой таблицей нет
- [x] Нет, CHECK видит только значения своей строки и константы
- С другой таблицей да, с SYSDATE нет
> CHECK должен давать одинаковый результат всегда, поэтому `SYSDATE`, последовательности, подзапросы и функции пользователя в нём запрещены. Межтабличные правила — это FK или триггер.
