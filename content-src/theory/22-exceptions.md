## Как работают исключения

Когда при выполнении возникает ошибка, Oracle **возбуждает исключение**: выполнение раздела `BEGIN` прекращается и управление переходит в раздел `EXCEPTION` **этого блока**. Если подходящего обработчика там нет — исключение уходит в **внешний** блок, и так до самого верха. Если его не обработал никто — ошибка возвращается клиенту.

```sql
BEGIN
  SELECT salary INTO v_sal FROM employees WHERE employee_id = p_id;
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    v_sal := 0;
  WHEN TOO_MANY_ROWS THEN
    RAISE;                -- пробросить дальше то же исключение
END;
```

После обработки выполнение продолжается **после блока**, где обработано исключение — вернуться в место ошибки нельзя. Чтобы после ошибки продолжить цикл, тело цикла оборачивают во вложенный блок `BEGIN … EXCEPTION … END`.

## Предопределённые исключения

У частых ошибок Oracle есть имена:

| Исключение | Код | Когда |
|---|---|---|
| `NO_DATA_FOUND` | ORA-01403 | SELECT INTO не нашёл строк; чтение несуществующего элемента ассоциативного массива |
| `TOO_MANY_ROWS` | ORA-01422 | SELECT INTO вернул больше одной строки |
| `ZERO_DIVIDE` | ORA-01476 | деление на ноль |
| `VALUE_ERROR` | ORA-06502 | не влезло в переменную, ошибка преобразования, NULL в NOT NULL |
| `INVALID_NUMBER` | ORA-01722 | строка не преобразуется в число **в SQL** |
| `DUP_VAL_ON_INDEX` | ORA-00001 | нарушение уникального индекса |
| `CURSOR_ALREADY_OPEN`, `INVALID_CURSOR` | ORA-06511, ORA-01001 | ошибки управления курсором |
| `CASE_NOT_FOUND` | ORA-06592 | ни одна ветка CASE-оператора не подошла |
| `COLLECTION_IS_NULL`, `SUBSCRIPT_BEYOND_COUNT` | ORA-06531, ORA-06533 | ошибки работы с коллекциями |

## Свои исключения

**Объявить и возбудить своё исключение:**

```sql
DECLARE
  e_low_salary EXCEPTION;
BEGIN
  IF v_sal < 1000 THEN
    RAISE e_low_salary;
  END IF;
EXCEPTION
  WHEN e_low_salary THEN …
END;
```

Если такое исключение выйдет за пределы базы без обработки, клиент увидит `ORA-06510: unhandled user-defined exception` — без понятного текста.

**Дать имя ошибке Oracle без имени** — `PRAGMA EXCEPTION_INIT`:

```sql
DECLARE
  e_child_exists EXCEPTION;
  PRAGMA EXCEPTION_INIT(e_child_exists, -2292);   -- ORA-02292
BEGIN
  DELETE FROM departments WHERE department_id = 60;
EXCEPTION
  WHEN e_child_exists THEN
    DBMS_OUTPUT.PUT_LINE('В отделе есть сотрудники');
END;
```

## RAISE_APPLICATION_ERROR

Чтобы вернуть клиенту **свою ошибку с понятным текстом и кодом**:

```sql
IF p_amount <= 0 THEN
  RAISE_APPLICATION_ERROR(-20001, 'Сумма должна быть положительной: ' || p_amount);
END IF;
```

- коды — от **-20000 до -20999**;
- текст до 2048 байт;
- третий параметр `TRUE` — добавить ошибку к стеку, не теряя предыдущих: `RAISE_APPLICATION_ERROR(-20002, 'Не удалось провести платёж', TRUE)`.

Поймать такую ошибку можно через `PRAGMA EXCEPTION_INIT(e, -20001)`. Обычно коды ошибок приложения объявляют константами и исключениями в одном пакете.

## SQLCODE, SQLERRM и стек

Внутри обработчика:

- `SQLCODE` — номер ошибки (отрицательный, у NO_DATA_FOUND — +100, у своих исключений — +1);
- `SQLERRM` — текст сообщения (до 512 символов);
- `DBMS_UTILITY.FORMAT_ERROR_STACK` — полный стек ошибок;
- `DBMS_UTILITY.FORMAT_ERROR_BACKTRACE` — **где** (в какой строке какого объекта) возникла ошибка. Без него при перехвате и логировании номер строки теряется.

`SQLCODE` и `SQLERRM` нельзя использовать напрямую в SQL-команде: сначала сохраняют их в переменные, потом вставляют.

## WHEN OTHERS — где хорошо, где плохо

`WHEN OTHERS` ловит **любое** исключение. Опасный антипаттерн:

```sql
EXCEPTION
  WHEN OTHERS THEN NULL;     -- ошибка проглочена, никто о ней не узнает
```

Транзакция продолжится в непонятном состоянии, данные испортятся молча. Компилятор даже предупреждает (PLW-06009). Правильный шаблон — залогировать и пробросить:

```sql
EXCEPTION
  WHEN OTHERS THEN
    log_error(SQLCODE, SQLERRM, DBMS_UTILITY.FORMAT_ERROR_BACKTRACE);  -- автономная транзакция
    RAISE;
END;
```

`WHEN OTHERS` ставится последним. Исключения, возникшие **в разделе DECLARE** (например, при инициализации переменной) или **внутри самого обработчика**, этим же блоком не перехватываются — они уходят во внешний блок.

## ? Как обрабатываются исключения в PL/SQL?

При ошибке управление переходит в раздел EXCEPTION текущего блока; ищется обработчик WHEN с подходящим именем, затем WHEN OTHERS. Нет обработчика — исключение распространяется во внешний блок и выше, до клиента. После обработки выполнение продолжается после блока, а не с места ошибки. Чтобы продолжить цикл после ошибки строки, тело оборачивают во вложенный блок с EXCEPTION.

## ? Какие предопределённые исключения ты знаешь?

NO_DATA_FOUND (SELECT INTO без строк), TOO_MANY_ROWS (больше одной строки), ZERO_DIVIDE, VALUE_ERROR (переполнение, ошибка преобразования в PL/SQL), INVALID_NUMBER (ошибка преобразования в SQL), DUP_VAL_ON_INDEX (нарушение уникальности), INVALID_CURSOR, CURSOR_ALREADY_OPEN, CASE_NOT_FOUND, исключения коллекций.

## ? Чем RAISE отличается от RAISE_APPLICATION_ERROR?

RAISE возбуждает именованное исключение (своё или предопределённое) либо, без аргумента внутри обработчика, пробрасывает текущее. RAISE_APPLICATION_ERROR создаёт ошибку с кодом из диапазона -20000…-20999 и своим текстом, которую клиент увидит как обычную ORA-ошибку с понятным сообщением. Своё исключение через RAISE, не обработанное до клиента, дало бы безликое ORA-06510.

## ? Почему WHEN OTHERS THEN NULL — плохая практика?

Глотает любую ошибку: ни вызывающий код, ни пользователь не узнают о проблеме, транзакция продолжается с частично выполненной работой, данные портятся молча, отладка становится невозможной. WHEN OTHERS допустим, если он логирует ошибку (с backtrace) и затем делает RAISE, либо осознанно превращает ошибку в понятную через RAISE_APPLICATION_ERROR.

## ? Что такое PRAGMA EXCEPTION_INIT?

Директива компилятору, связывающая своё объявленное исключение с номером ошибки Oracle. Позволяет писать понятный обработчик `WHEN e_child_exists` вместо проверки SQLCODE в WHEN OTHERS. Работает и для ошибок из RAISE_APPLICATION_ERROR (-20000…-20999).

## ? Как узнать, в какой строке возникла ошибка?

DBMS_UTILITY.FORMAT_ERROR_BACKTRACE — возвращает стек с объектами и номерами строк, где исключение было возбуждено. SQLERRM даёт только текст, а при перехвате и повторном RAISE исходный номер строки теряется, поэтому backtrace сохраняют в лог прямо в обработчике. В 12c+ есть пакет UTL_CALL_STACK.

## ? Что будет, если исключение возникнет в разделе DECLARE?

Его не поймает раздел EXCEPTION того же блока — оно сразу уйдёт во внешний блок. Например, `v NUMBER(2) := 100;` даст VALUE_ERROR, который обработчик этого блока не увидит. То же — для исключения, возникшего внутри самого обработчика.
