## Оптимизатор и статистика

Для каждого запроса Oracle выбирает **план выполнения**: в каком порядке читать таблицы, через индекс или полностью, каким методом соединять. Выбирает **стоимостный оптимизатор** (CBO): перебирает варианты и оценивает их «стоимость» по **статистике**:

- сколько строк и блоков в таблице;
- сколько разных значений в столбце, сколько NULL, минимум и максимум;
- **гистограммы** — распределение значений, если оно неравномерное (90% заказов в статусе DONE, 1% — NEW);
- характеристики индексов (высота, фактор кластеризации).

Статистику собирают `DBMS_STATS` (обычно это делает автоматическое ночное задание):

```sql
EXEC DBMS_STATS.GATHER_TABLE_STATS(USER, 'EMPLOYEES');
```

Устаревшая статистика (таблица выросла в 100 раз после последнего сбора) — частая причина плохих планов: оптимизатор думает, что строк мало, и выбирает Nested Loops там, где нужен Hash Join.

## Как посмотреть план

```sql
EXPLAIN PLAN FOR
SELECT e.last_name, d.department_name
  FROM employees e JOIN departments d ON d.department_id = e.department_id
 WHERE e.salary > 10000;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
```

`EXPLAIN PLAN` показывает **предполагаемый** план, без выполнения запроса. Реальный план выполненного запроса — с фактическим количеством строк:

```sql
SELECT /*+ GATHER_PLAN_STATISTICS */ … ;
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));
```

Главное в таком плане — сравнить **E-Rows** (оценка оптимизатора) и **A-Rows** (сколько строк было на самом деле). Расхождение в десятки раз — оптимизатор ошибся в оценке, и, скорее всего, здесь корень проблемы.

## Как читать план

План — дерево операций. Читается **изнутри наружу и сверху вниз**: сначала выполняются самые вложенные (с наибольшим отступом) операции; у соединения первый потомок — ведущий (внешний) набор.

Что смотреть:

| Что видим | О чём думать |
|---|---|
| `TABLE ACCESS FULL` большой таблицы, а нужно несколько строк | нет индекса, или его выключила функция над столбцом, неявное преобразование, `LIKE '%…'` |
| `INDEX RANGE SCAN` + тысячи `TABLE ACCESS BY INDEX ROWID` | индекс неселективен — полное сканирование может быть дешевле |
| `NESTED LOOPS` с большим внешним набором | неверная оценка строк, нужен Hash Join |
| `MERGE JOIN CARTESIAN` | пропущено условие соединения |
| `SORT ORDER BY` / `HASH GROUP BY` с уходом в TEMP | не хватает памяти, сортировка большого объёма |
| `Cost`, `Rows`, `Bytes` | оценки оптимизатора, не время |

## Хинты

**Хинт** — указание оптимизатору в комментарии `/*+ … */` сразу после SELECT/UPDATE/…:

```sql
SELECT /*+ INDEX(e emp_dept_ix) */ … FROM employees e WHERE …;
SELECT /*+ FULL(e) PARALLEL(e 4) */ … ;
SELECT /*+ LEADING(d e) USE_HASH(e) */ … ;
```

Частые: `INDEX`, `FULL`, `USE_NL`, `USE_HASH`, `LEADING`, `PARALLEL`, `APPEND` (прямая вставка в обход буферного кэша), `FIRST_ROWS(n)`.

Хинт с ошибкой (опечатка в имени алиаса) **молча игнорируется**. Хинты — последнее средство: они «цементируют» план, который через год, с другими объёмами данных, может стать плохим. Сначала — статистика, индексы, переписывание запроса; для фиксации плана без изменения кода есть **SQL Plan Baselines** и SQL Profiles.

## Производительность PL/SQL

Рецепты, которые ждут на собеседовании:

1. **Делай в SQL то, что можно сделать в SQL** — одна команда вместо цикла.
2. **BULK COLLECT / FORALL** вместо построчной обработки — меньше переключений контекста.
3. **Bind-переменные** — меньше hard parse (в статическом PL/SQL — автоматически).
4. **Функции в SQL** — `DETERMINISTIC`, `RESULT_CACHE`, `PRAGMA UDF`, скалярный подзапрос для кэширования; лучше — переписать на SQL.
5. **Не коммитить в цикле.**
6. **Кэшировать справочники** в ассоциативном массиве пакета вместо запроса на каждую строку.
7. **Типы:** `PLS_INTEGER`/`SIMPLE_INTEGER` для счётчиков быстрее, чем `NUMBER`.
8. **NOCOPY** для больших коллекций в OUT/IN OUT параметрах.

Инструменты измерения: `DBMS_UTILITY.GET_TIME` (сотые доли секунды) для простого замера, **DBMS_HPROF** (иерархический профайлер — какая подпрограмма сколько времени заняла), `DBMS_PROFILER` (построчно), **SQL Trace / TKPROF** (`DBMS_MONITOR.SESSION_TRACE_ENABLE`) — все SQL сессии с временем и планами, **AWR/ASH** — нагрузка на базу за период.

## «Запрос тормозит — что будешь делать?»

Хороший структурированный ответ:

1. **Воспроизвести и измерить:** сколько выполняется, сколько строк возвращает, всегда ли медленно или только с некоторыми параметрами (bind peeking).
2. **Посмотреть фактический план** — `DBMS_XPLAN.DISPLAY_CURSOR` с `ALLSTATS LAST` или SQL Monitor: где больше всего времени и строк, где E-Rows сильно расходится с A-Rows.
3. **Проверить статистику** по таблицам и индексам — актуальна ли.
4. **Проверить индексы и условия:** нужные индексы есть? не выключены ли функцией, неявным преобразованием, `OR`, `NOT IN`?
5. **Переписать запрос:** убрать лишние соединения и DISTINCT, заменить коррелированные подзапросы, NOT IN на NOT EXISTS, функции в WHERE — на диапазоны.
6. **Посмотреть на ожидания** (блокировки, ввод-вывод) — может, проблема не в плане, а в том, что запрос ждёт другую сессию.
7. Только потом — хинты, baseline, секционирование, материализованные представления.

## ? Что такое план выполнения и как его посмотреть?

Последовательность операций, которой Oracle выполняет запрос: способы доступа к таблицам (полное сканирование, индекс), порядок и методы соединений, сортировки. Посмотреть предполагаемый план — EXPLAIN PLAN FOR … и DBMS_XPLAN.DISPLAY; фактический для выполненного запроса — DBMS_XPLAN.DISPLAY_CURSOR (с GATHER_PLAN_STATISTICS — с реальным количеством строк), а также автотрассировка в клиенте и SQL Monitor.

## ? Что такое статистика и зачем она оптимизатору?

Сведения о данных: количество строк и блоков, число различных значений и NULL в столбцах, гистограммы распределения, параметры индексов. Стоимостный оптимизатор по ним оценивает, сколько строк вернёт каждый шаг, и выбирает дешёвый план. Устаревшая статистика — частая причина плохих планов. Собирается DBMS_STATS, обычно автоматическим заданием.

## ? Что такое хинты и почему их стоит использовать осторожно?

Подсказки оптимизатору в комментарии /*+ … */: какой индекс использовать, порядок и метод соединения, параллелизм. Осторожно — потому что фиксируют план, который при росте данных может стать плохим, а ошибочный хинт молча игнорируется. Сначала исправляют причину (статистика, индексы, запрос), для фиксации плана есть SQL Plan Baselines.

## ? Запрос стал выполняться медленно. Твои действия?

Измерить и воспроизвести; получить фактический план (DISPLAY_CURSOR, ALLSTATS LAST) и найти шаг, где расходятся оценка и реальность или тратится больше всего времени; проверить актуальность статистики; проверить индексы и не выключены ли они функциями или неявным преобразованием; переписать запрос; проверить ожидания и блокировки; в последнюю очередь — хинты и фиксация плана.

## ? Как ускорить PL/SQL-код, который обрабатывает миллион строк в цикле?

Сначала попробовать заменить цикл одной SQL-командой (UPDATE/INSERT … SELECT/MERGE). Если процедурная логика нужна — BULK COLLECT с LIMIT и FORALL, чтобы сократить переключения контекста. Убрать COMMIT из цикла, кэшировать справочники в памяти, не вызывать функции с SQL внутри на каждой строке. Замерить профайлером (DBMS_HPROF), где реально тратится время.

## ? Чем EXPLAIN PLAN отличается от реального плана?

EXPLAIN PLAN показывает план, который оптимизатор построил бы сейчас, не выполняя запрос, — он может отличаться от реального: другие значения bind-переменных (bind peeking), другая среда сессии, неявные преобразования типов. Реальный план выполненного курсора берут из V$SQL_PLAN через DBMS_XPLAN.DISPLAY_CURSOR.

## ? Какими инструментами ты профилируешь PL/SQL и SQL?

DBMS_UTILITY.GET_TIME для простых замеров; DBMS_HPROF — иерархический профайлер PL/SQL (время по подпрограммам); DBMS_PROFILER — построчно; SQL Trace + TKPROF — все SQL сессии с временем и ожиданиями; DBMS_XPLAN и SQL Monitor — для отдельных запросов; AWR/ASH — картина нагрузки на базу.
